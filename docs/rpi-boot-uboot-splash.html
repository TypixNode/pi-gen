树莓派启动原理、U-Boot 对比与彩虹屏定制指南

启动加载流程 · U-Boot 与固件直启 Linux 的区别 · 彩虹屏的真相与开机画面定制方案

一、技术原理与启动加载流程

树莓派与绝大多数 ARM 开发板最大的不同是：它是"GPU 先启动"的架构。 上电后先运行的不是 ARM CPU，而是 Broadcom SoC 里的 VideoCore GPU。 整个启动早期阶段由 GPU 上运行的闭源固件完成，ARM 核心直到内核（或 U-Boot）被加载好之后才被"唤醒"。

1. 默认启动链（Raspberry Pi 1 – 3 / Zero 系列）

① BootROMSoC 内部固化的只读代码，由 GPU 执行，负责找到启动介质
→
② bootcode.bin位于 TF 卡 FAT 分区（boot 分区），第二阶段引导，初始化 SDRAM
→
③ start.elf + fixup.datGPU 主固件：读取 config.txt、显示彩虹屏、加载内核与设备树
→
④ kernel8.img 等ARM 核心被释放，直接从内核入口开始执行 Linux

2. Raspberry Pi 4 / 5 的差异

  • Pi 4：bootcode.bin 被板载 SPI EEPROM 中的引导程序取代（可网络启动、USB 启动、可升级），之后仍加载 start4.elf，流程与上面一致。
  • Pi 5：更进一步，start.elf 系列被彻底移除，EEPROM 引导程序直接加载内核/设备树。因此 Pi 5 上没有彩虹屏，取而代之的是固件自绘的诊断/自检画面。

3. boot 分区上各文件的角色

文件作用
bootcode.bin第二阶段引导（Pi 1–3；Pi 4/5 已移入 EEPROM）
start*.elf / fixup*.datGPU 主固件及其内存分配配置（Pi 5 无此文件）
config.txt固件的"BIOS 设置"：超频、显示、设备树 overlay、指定内核文件名等
cmdline.txt传给 Linux 内核的命令行参数（单行）
kernel8.img / kernel_2712.img 等Linux 内核镜像（也可以换成 u-boot.bin）
bcm27xx-*.dtb、overlays/设备树及其 overlay，由固件加载并动态修补后传给内核

在本仓库（pi-gen）中，config.txt 与 cmdline.txt 的模板位于 stage1/00-boot-files/files/，由 stage1/00-boot-files/00-run.sh 安装到镜像的 /boot/firmware/；固件与内核文件由 stage2 安装的 raspberrypi-bootloader / linux-image-* 等 deb 包提供。

二、U-Boot 启动与默认直启 Linux 内核的区别

关键点：U-Boot 并不替代树莓派的 GPU 固件，而是"插在"固件和 Linux 之间。 做法是在 config.txt 里写 kernel=u-boot.bin，让固件把 U-Boot 当成"内核"来加载；之后由 U-Boot 负责真正加载 Linux 内核、设备树和 initramfs。

固件直启（默认）BootROM → 固件 → Linux 内核
对比
U-Boot 方式BootROM → 固件 → u-boot.bin → boot.scr / extlinux.conf → Linux 内核
维度固件直启 Linux（树莓派默认）经由 U-Boot 启动
启动链长度 短，开机更快 多一级引导，略慢（约多 1–2 秒）
配置方式 config.txt + cmdline.txt，树莓派私有格式 U-Boot 环境变量、boot.scr 脚本、标准 extlinux.conf（Distro Boot）
交互能力 无。固件不可交互、闭源 有串口/HDMI 命令行 shell，可手动加载内核、读写内存、烧写、调试
多系统 / A-B 冗余 依赖 autoboot.txt/tryboot 机制，能力有限 脚本任意编排：启动菜单、多内核选择、失败自动回滚、看门狗配合
网络 / 脚本启动 Pi 4/5 的 EEPROM 支持 PXE，但逻辑固定 TFTP、NFS、HTTP、USB、NVMe……加载逻辑完全可编程
设备树处理 固件加载 DTB 并自动应用 overlay、注入内存/MAC 等信息 通常配置 U-Boot 复用"固件已修补好"的 DTB；若 U-Boot 自己加载 DTB，会丢失固件的动态修补，overlay 需另行处理（常见坑）
生态与可移植性 树莓派专属 嵌入式行业标准：Yocto、Buildroot、OpenWrt、Home Assistant OS、Debian 通用 arm64 镜像都用它
典型使用场景 桌面/日常使用，追求简单和快 产品化设备：OTA 升级、双分区回滚、统一多平台引导、启动画面定制
一句话总结 默认方式 = 简单、快、够用；U-Boot = 多一级可编程的引导层，换来标准化、可交互、可定制（包括在引导阶段显示自定义图片）。 另外注意：彩虹屏发生在固件阶段，在 U-Boot 之前，所以换用 U-Boot 并不会去掉彩虹屏。

三、彩虹屏在哪个环节、哪个文件？能定制吗？

它属于哪个环节？

彩虹屏出现在第 ③ 阶段——GPU 主固件 start.elf（Pi 4 上是 start4.elf）运行时， 也就是固件初始化显示输出之后、Linux 内核（或 U-Boot）接管之前。它同时充当 GPU 的显示自检图。

具体是哪个文件？

重要结论：它不是一张图片文件 彩虹图案是 start.elf 固件在运行时用代码程序化生成的渐变测试图， 并不存在于 TF 卡上的任何 PNG/BMP 文件里。而 start.elf 是 Broadcom/树莓派基金会的 闭源二进制固件，没有公开源码和资源段格式，因此彩虹屏本身无法被替换成自定义图片。

你唯一能做的官方操作是在 config.txt 中关闭它：

# /boot/firmware/config.txt
disable_splash=1

容易混淆的三种"彩虹"

现象含义
开机短暂全屏彩虹正常现象：固件显示自检图，随后交给内核
永远停在彩虹屏故障：固件找不到或无法启动内核（kernel 文件损坏/缺失、config.txt 指错文件等）
屏幕右上角小彩虹方块旧固件的欠压警告（新固件改为闪电图标），与开机彩虹屏无关

四、想要自定义开机图片：从 TF 卡 boot 分区读取，哪种方式最方便？

既然彩虹屏本体不可替换，思路就变为：关掉彩虹屏（disable_splash=1）， 然后在启动链中尽早的、你可控的环节显示自己的图片。按出现时机从早到晚，共有四种方案：

方案 A：U-Boot 显示 BMP（可直接读 boot 分区，最早的可定制画面）

这正好回应了你的想法——U-Boot 可以直接从 TF 卡 FAT 分区读取图片文件并显示， 改图只需替换 boot 分区里的一个 BMP，无需重新编译任何东西：

# 编译 U-Boot 时启用（rpi_arm64_defconfig 基础上）：
#   CONFIG_VIDEO=y  CONFIG_CMD_BMP=y  CONFIG_SPLASH_SCREEN=y

# config.txt 里：
kernel=u-boot.bin
disable_splash=1

# U-Boot 环境（或 boot.scr 脚本）里：
fatload mmc 0:1 ${loadaddr} splash.bmp
bmp display ${loadaddr} m m        # m m = 水平垂直居中
# 也可用 splashimage / splashfile / splashpos 环境变量自动显示

注意：图片须为未压缩的 BMP（建议 24 位或 8 位）；且这要求你本来就打算用 U-Boot， 否则单为一张图引入 U-Boot 有点重。

方案 B：initramfs / systemd 早期用 fbi 画图（不用 U-Boot 也能"读 boot 分区"）

把图片放在 boot 分区（FAT，插到任何电脑上都能改），内核起来后第一时间用 framebuffer 工具显示它。出现时机约在上电后 3–5 秒：

# 图片放到 /boot/firmware/splash.png
sudo apt install fbi

# /etc/systemd/system/splashscreen.service
[Unit]
DefaultDependencies=no
After=local-fs.target

[Service]
ExecStart=/usr/bin/fbi -d /dev/fb0 --noverbose -a /boot/firmware/splash.png
StandardInput=tty
StandardOutput=tty

[Install]
WantedBy=sysinit.target

配合 cmdline.txt 加 quiet logo.nologo 隐藏内核日志和小树莓 logo 效果更佳。

方案 C：Plymouth 主题（Raspberry Pi OS 官方方式，最省事）

Raspberry Pi OS 桌面版自带 Plymouth，开机画面用的是 pix 主题，直接替换其中一张 PNG 即可：

sudo cp my-splash.png /usr/share/plymouth/themes/pix/splash.png
sudo update-initramfs -u     # 若启用了 initramfs 则需刷新

缺点：图片在 ext4 根分区而不是 boot 分区，且出现时机比方案 B 稍晚。

方案 D：替换内核内置 logo（不推荐）

内核启动时角落的小树莓是编译进内核的 CONFIG_LOGO（logo_linux_clut224.ppm）， 改它必须重新编译内核，改一次图重编一次，最不方便。

怎么选？

方案图片位置出现时机改图成本推荐场景
A：U-Boot BMPboot 分区（FAT）最早（内核之前）替换 BMP 即可本来就用 U-Boot 的产品化设备
B：fbi + boot 分区图片boot 分区（FAT）内核起来后 ~3–5 秒替换 PNG 即可不想引入 U-Boot 时的最方便方案
C：Plymouth根分区稍晚于 B替换 PNG（可能需刷 initramfs）Raspberry Pi OS 桌面版日常定制

结论 "彩虹屏那张图"改不了（闭源固件运行时生成，无对应文件），只能用 disable_splash=1 关掉。 如果你已经在用 U-Boot，方案 A 完全满足"直接读 TF 卡 boot 分区里的图片"的需求； 如果不用 U-Boot，方案 B（图片放 boot 分区 + fbi 显示）是综合最方便的选择—— 图片在 FAT 分区、任何电脑都能替换，也不需要重编译任何组件。 在 pi-gen 中落地时：disable_splash=1 加进 stage1/00-boot-files/files/config.txt， splash 图片与 systemd 服务可以做成一个自定义 stage 安装进镜像。
