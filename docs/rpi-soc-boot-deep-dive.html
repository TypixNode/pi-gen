一、完整启动加载流程（可视化）

核心反常识点：上电时 ARM CPU 处于 reset（关闭）状态，是 GPU（VideoCore）先启动，并作为启动信任根，一路把硬件初始化好、把内核加载进内存之后，才"放开"ARM 让它执行 Linux。

① BootROM（SoC 内固化）
GPU 执行；SDRAM 尚未启用。从启动介质寻找并把下一级载入 L2 cache
▼
② 第二级引导
Pi 1/2/3：从 FAT 分区读 bootcode.bin 到 L2 cache，初始化 SDRAM  |  Pi 4/5：改为板载 SPI EEPROM 里的引导程序（可 USB/网络/NVMe 启动、可升级）
▼
③ GPU 主固件 start.elf（+ fixup.dat）
读 dt-blob.bin（GPU 侧设备树：GPIO/时钟）→ 读 config.txt → 显示彩虹自检图
 → 加载机型专属 ARM DTB 并合并 overlay → 划分 GPU/ARM 内存（fixup.dat 提供重定位信息）
▼
④ 加载内核 + cmdline.txt
把 kernel*.img、initramfs、合并后的设备树放入 ARM 内存；可选执行 armstub 配置 CPU 状态
▼
⑤ 释放 ARM 出 reset
GPU 让 ARM 从内核入口开始执行 Linux；此后 VPU 固件退居后台，通过 mailbox/RPC 提供服务
▼
⑥ Linux 内核 → init / systemd
用户空间启动
Pi 5 / CM5 的重要差异 BCM2712 机型的固件完全自包含在 EEPROM 里，不再有 start.elf 那一套，EEPROM 引导程序直接加载 kernel_2712.img；且固件会先校验设备树是否兼容再启动（否则旧内核会直接挂住）。因此 Pi 5 没有经典彩虹屏。

overlay（设备树覆盖）到底谁在读？

关键点：是 GPU 固件（start.elf / EEPROM 引导程序）在把内核拉起来之前就读取并合并 overlay 的，不是 Linux 内核。顺序是：

  1. start.elf 先读 dt-blob.bin —— 这是"GPU 专用设备树"，决定早期 GPIO 状态、GPU 时钟等；
  2. 再读 config.txt，据此确定要加载哪个基础 DTB、以及 dtoverlay= / dtparam= 指定的一堆 overlay；
  3. 固件把 base DTB 与所有 overlay 在内存里合并成最终设备树，再连同动态注入的信息（内存大小、MAC、时钟、DMA 通道等）一起交给内核；
  4. os_prefix 可让同一张卡放多套内核/DTB/overlay 并切换。

这就是为什么"改 config.txt 里的 overlay"能改变硬件枚举——真正干活的是固件阶段，而不是内核在运行时去读 boot 分区。

二、SoC 内部各模块框图（每块都标注用途）

树莓派用的 Broadcom BCM2xxx 本质上是一颗以 VideoCore 多媒体协处理器为核心、把 ARM"挂在旁边"的 SoC。下图把一颗典型 BCM SoC 拆成模块，每个小框都标了它是什么、干什么：

Broadcom BCM2xxx SoC（单芯片集成）
协处理器 · 引导核心
VPU — 双核 VideoCore 标量/向量处理器 @250MHz

真正的"主处理器"。上电即运行，负责整个启动、电源管理、时钟、视频输出协调。运行闭源 ThreadX RTOS，bootcode.bin/start.elf 都在它上面执行。标量(整型+浮点)+整型向量 SIMD。

GPU · 计算
QPU — Quad Processor Units（3D/着色器）

并行浮点着色单元，约 24 GFLOPS，处理顶点/像素着色与通用计算。这部分的文档与驱动是 2014 年 Broadcom 唯一开源的部分（Mesa VC4/V3D 驱动）。

GPU · 影像
ISP 图像信号处理

镜头阴影校正、畸变校正、统计信息，服务于摄像头（CSI）。

GPU · 编解码
硬件视频编解码

H.264 / H.265 硬解硬编（各代能力不同），BCM 芯片本行就是机顶盒多媒体。

GPU · 显示
显示 / HDMI / DSI 输出管线

帧缓冲、HDMI 输出、DSI 屏接口。彩虹自检图就是这块被 VPU 固件点亮后画出来的。

应用处理器
ARM CPU 集群（跑 Linux 的那个）

逐代升级：单核 ARM11 → 四核 A7 → A53 → A72 → A76。上电时被保持在 reset，直到 GPU 把内核准备好才被释放。逻辑上是"外挂"在 VideoCore 旁边的。

存储控制
SDRAM 控制器 / 内存分割

由第二级引导启用 SDRAM；GPU 与 ARM 共享内存，比例由固件（fixup.dat / config.txt）划分。

缓存
L1 / L2 Cache

bootcode.bin 最初就是被载入 L2 cache 中执行（SDRAM 尚未就绪）。

I/O · 外设
外设：SD/eMMC · USB · I2C/SPI/UART · GPIO · 以太网 · PCIe*

CM 的板载 eMMC 就接在"主 SD 卡接口"上。PCIe 从 BCM2711(Pi4) 起引入。各外设默认关闭，靠设备树 + overlay 启用。

Pi 5 专属 · 自研南桥
RP1 I/O 控制器（仅 BCM2712 / Pi 5 系列，独立芯片）

树莓派自研，把 USB 3.0/2.0、千兆以太网、GPIO、部分外设从主 SoC 剥离到独立南桥，经 PCIe 连接。这是 Pi 5 相较此前所有代际最大的架构变化之一。

VideoCore（GPU/协处理器，闭源固件运行处） ARM 应用处理器（跑 Linux） 存储/缓存 I/O 与外设

* PCIe 自 Pi 4 (BCM2711) 引入；RP1 南桥为 Pi 5 (BCM2712) 独有。

三、逆向出来的 ISA 与 RTOS（公开 + 私有信息）

哪些是公开的、哪些是私有的 私有（Broadcom 从未公开）：start.elf/bootcode.bin 的源码、VPU 引导固件逻辑、VideoCore 完整 ISA 官方手册。
公开（官方）：仅 2014 年开源的 QPU 3D 图形核心文档与驱动（BSD 许可）。
社区逆向得到的：VPU 指令集、寄存器映射、反汇编器、以及"VPU 上跑 ThreadX"这一结论——全部来自 Herman Hermitage 等人的逆向与专利研究。

VPU（VideoCore IV 标量/向量核）ISA —— 逆向结论

  • 32 个寄存器，可存整数或 32 位浮点（浮点与整数共用寄存器）；
  • 类 ARM 的 32 位三操作数指令，外加一批 16 位双操作数短指令；
  • 存在 48 位指令形态，可直接携带完整 32 位立即数（不用 ARM 那种常量池，也不用 PowerPC 的拆分立即数）；
  • 双核 + 集成中断控制器；
  • 内建 80 位向量 DSP，工作在一个 64×64×8bit 的"方形寄存器阵列"上，可按行/按列访问做 SIMD——面向视频解码；
  • 类 ARM 的条件执行、寄存器批量 load/save（push/pop）、DSP 式饱和运算与定点支持。

QPU（3D 着色器核）ISA —— 官方 2014 已公开

  • 定长 64 位指令字，单条指令内含多个发射槽（Add 向量 ALU + Multiply 向量 ALU）；
  • 分支有 3 个延迟槽；线程切换靠协作式 thread-switch 指令；
  • 寄存器写后需隔 1 个指令周期才能读回；程序以带 program-end 信号的指令结束。

RTOS：ThreadX

整颗 SoC 在启动期由载入 VPU 的 ThreadX RTOS（Express Logic 的商用实时系统，后为微软 Azure RTOS）管理。start.elf 本质就是"ThreadX + 一堆固件服务"的打包二进制。ARM 上的 Linux 起来后，VPU 仍在后台跑 ThreadX，通过 mailbox/RPC 为 Linux 提供时钟、电源、显示、编解码等服务。

能逆向、能改吗（呼应上一问） ISA 已被逆向、有反汇编器，所以逆向可行；但直接改 start.elf 极不划算（无符号、私有 ISA+RTOS、新板有 secure boot 签名校验、且涉及 Broadcom IP）。务实路线是用 config.txt 配置，或用 kernel=u-boot.bin 把控制权交给开源可编程的 U-Boot 阶段。曾有 rpi-open-firmware 尝试开源替代，但仅在早期 Pi 上实验性可用，不支持 Pi 3/4/5。

要点：GPU 从 Pi 1–3 一直是 VideoCore IV，Pi 4 才升到 VI、Pi 5 到 VII；引导方式从"SD 上的 bootcode.bin"演进到"板载 EEPROM"，Pi 5 更是把整套固件都塞进 EEPROM。overlay 合并机制各代一致（都在固件阶段完成），但 Pi 5 增加了"启动前校验 DTB 兼容性"。

五、Compute Module（CM）与"板载 eMMC 设备"的逐代差异

普通 Pi 从可插拔 SD 卡启动；Compute Module 把 eMMC 闪存直接焊在模块上，接到 SoC 的"主 SD 卡接口"。这带来一套专门的烧录/启动机制（rpiboot/usbboot：让模块以 USB 大容量存储设备出现在主机上再写入）。逐代差异如下：

启动介质与烧录机制

模块SoC进入烧录模式USB gadget 机制专属设备树备注
CM1BCM2835 nRPI_BOOT/EMMC-DISABLE 跳线 旧式 msd 固件接口（legacy） bcm2708-rpi-cm.dtb 引导返回的 USB 包略有瑕疵，个别主机 USB 口不识别
CM3 / CM3+BCM2837 EMMC-DISABLE 跳线 现代 Linux mass-storage gadget（更可靠，支持 UART 控制台） bcm2710-rpi-cm3.dtb 修复了 CM1 的 USB 包 bug；少数因 FAT32 分区时序问题需手动建分区
CM4 / CM4SBCM2711 nRPIBOOT = GPIO 40 拉低，否则加载 SPI EEPROM gadget + rpiboot 还用于更新 EEPROM；推荐用 boot.img CM4 专属 DTB 引入 SPI EEPROM 引导；绿灯由软件 bootloader 点亮
CM5BCM2712 nRPIBOOT = BCM2712 GPIO 20 拉低，否则加载 EEPROM rpiboot -d mass-storage-gadget64（用 Linux initramfs，带 UART/HDMI 登录台） CM5 专属 DTB EEPROM 默认支持 MMC / USB-MSD / 网络 / NVMe 启动
CM 与普通 Pi 在启动上的本质区别 ①存储：CM 用板载 eMMC（焊死、更可靠、需 rpiboot 烧录），普通 Pi 用可插拔 SD/USB。
②设备树策略：普通 Pi 有随机型固定的 DTB；CM 的基础 DTB几乎不定义 GPIO（除 eMMC/SD 引脚），把具体引脚功能交给用户自定义 overlay——因为 CM 是给你自己做载板的，引脚怎么用由载板决定。
③引导演化：CM1 老式 msd → CM3 现代 gadget → CM4/CM5 引入 SPI EEPROM 与 nRPIBOOT 跳线，CM5 的 EEPROM 直接支持 NVMe/网络启动。
这三点，就是"读 overlay、启动介质、GPU/固件"在 CM 与带 eMMC 机型上逐代变化的全部要点。

rpiboot 分阶段（CM4/CM5，来自官方 troubleshooting）

烧录过程本身就是一个"缩微版启动"：ROM → bootcode.bin → VPU 固件（start.elf）→（大容量存储 gadget 模式下）Linux initramfs。每一级都会断开并以新的 USB 描述符重新出现，可在主机 dmesg 里逐级看到。这也印证了前面的启动链模型。
